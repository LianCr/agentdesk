# AgentDesk — Bilingual Insurance Agent Copilot

Chinese-speaking insurance agents serve clients in Chinese, but their product
documents are in English. Every client question becomes a search through
dozens of PDF pages, and every answer carries the risk of saying something the
documents do not support.

AgentDesk closes that gap: **ask in Chinese, get an answer grounded in the
English source, with the page number and the verbatim quote attached** — and
when the documents do not contain the answer, it says so instead of inventing
one.

## What it does

### 1. Grounded bilingual Q&A

Ask in Chinese; the answer is in Chinese, the evidence is the original English.
Every factual claim carries a citation card with the document, the page, and
the exact English sentence — and a link that opens the PDF at that page.

Asked for a number the documents do not contain, it refuses:

```
资料不足 Insufficient evidence · INSUFFICIENT_EVIDENCE
现有资料不足以回答这个问题的核心内容。
```

…and still cites what the documents *do* say, then lists exactly what is
missing. Asked which product is "best", a deterministic rule stops it before
the model is ever called (`FINAL_RECOMMENDATION_REQUESTED`, zero citations).

### 2. Product comparison drafts

A 13-row fact table for any two products. **The table is generated by code, not
by a model** — the model does not choose facts, assign them to products,
compare numbers, decide what is "not applicable", pick evidence, or build
citations. Every factual cell traces to a document, page and verbatim quote.

Four availability states never collapse into each other: `available`,
`not_applicable`, `not_provided`, `conflict`. A documented *"This product does
not offer optional riders"* is a **cited fact**, not a blank. If a structured
value and the document disagree, the cell shows **nothing** and reports
`conflict` — fail closed.

It never ranks the two products. There is no score, no winner, no "better fit"
field anywhere in the data structure.

### 3. Human review workflow

A draft can be sent for review. The reviewer sees a **frozen snapshot** — the
facts as they were when the review was created, hashed, and immutable at the
database level — plus four axes that are deliberately kept apart:

| | |
|---|---|
| `comparisonStatus` | are the **facts** trustworthy? *(code)* |
| `workflowDecision` | how far may this **travel**? *(code)* |
| `requiredApprovalLevel` | how much **authority** does it need? *(code)* |
| `reviewState` | how far has the **work** actually got? *(a human)* |

Collapsing these into one "high risk" badge is the mistake this design exists
to prevent. A 67-year-old client replacing an existing annuity produces
`complete` + `block_client_draft` + `licensed_agent_required` +
`pending_review`: the facts check out, it must not go to a client, a licensed
agent has to look at it, and nobody has yet.

Approve / reject / request revision each append to an **append-only** audit
trail. Two tabs racing produce one decision and one event, not two.

### 4. Post-review automation

A completed review can create a follow-up task through an n8n webhook.

There is exactly **one kind of artifact: an internal task.** The task-type enum
has no client-facing member and the payload has no recipient field — so "this
can never be emailed to a client by mistake" is not a rule someone has to
remember, it is a value the system cannot express. Rejected reviews create
nothing. With no webhook configured, the result is labelled `Demo / mock`,
never `Delivered`.

Plus **voice input**: speak a question, review the transcript, then send it
yourself. It is never auto-submitted — across repeated runs English
transcribed exactly every time and Chinese got 有现金价值 wrong once in three,
which is precisely why a human confirms before anything is asked.

## How the claims above are checked

Not by asking a model whether it did well.

| Property | How it is enforced |
|---|---|
| No fabricated citation | Every quote must be an exact substring of the retrieved chunk; page and document metadata are **injected by code**, never produced by the model |
| No unsupported claim on screen | Claims that fail validation are dropped before render, with an integrity assertion |
| No ranking / no suitability | Deterministic rules run **before** the model; no score field exists in the schema |
| Facts never invented | A structured value that disagrees with its document renders nothing (`conflict`) |
| Reviewed artifact never changes | Database triggers reject any update to the snapshot, its hash, or the routing basis |
| Audit trail never rewritten | Append-only triggers refuse UPDATE entirely and DELETE except for test-prefixed rows |
| One decision, one event | Advisory lock + compare-and-set inside one transaction; a stale second writer gets a conflict and changes nothing |
| Automation can't reach a client | No client-facing task type and no recipient field exist |

Frozen evaluations, all deterministic and model-free where it matters:

- **[M3](docs/m3-evaluation.md)** — 30 frozen questions + 21 red-team probes.
  Deterministic invariants (unsourced facts on screen, wrong citation page,
  invalid quote) were **zero in every observed run**; the model-dependent
  quality metrics are reported as a distribution, not a single lucky number.
  The last recorded run scored 28/30 cases and 13/18 probes.
- **[M4](docs/m4-evaluation.md)** — 23 frozen comparison cases,
  **17/17 deterministic hard gates pass**, 16 mutation tests proving the
  evaluator can fail.
- **[M5](docs/m5-evaluation.md)** — 41 frozen workflow cases,
  **19/19 hard gates at zero**, 21 mutation tests. No model is involved in this
  evaluation at all.
- **[M6](docs/demo-acceptance.md)** — 10 end-to-end demo scenarios run in a
  browser, which found two defects no suite had.

Test suites: **369 unit · 77 database · 104 browser**. Knowledge base is frozen
at 3 documents / 20 pages / 45 chunks and verified unchanged by every run.

## What it deliberately does not do

- **No final recommendation, no suitability determination.** Not a limitation
  to fix later — it is the product boundary.
- **No authentication.** `"Demo Reviewer"` is a server-owned placeholder, not
  an identity claim.
- **No client communication capability at all.** Not disabled — absent.
- **Fictional data only.** No real carrier, product, client or PII.
- **Demo rules are not legal conclusions.** The age-65 threshold and
  replacement-review rules are this project's business policy for fictional
  products, and would need compliance and licensed-agent sign-off in reality.
- **No compliance certification is claimed.**

Gaps between this demo and a production system are enumerated in
**[docs/demo-to-production.md](docs/demo-to-production.md)** — including the
ones that are inconvenient.

## Architecture

```text
English product PDFs (generated from one source of truth)
   │  heading/table-aware chunking, page metadata
   ▼
Supabase Postgres + pgvector ── RLS on, zero policies, no client access
   │
   ├─► Q&A:        zh query ─► multi-route retrieval ─► strict-schema draft
   │                          ─► code verifies every quote ─► grounded answer
   │
   ├─► Compare:    products.json ─► fact registry ─► 13-row table (no model)
   │                          ─► optional neutral narrative, guard-checked
   │
   ├─► Review:     server rebuilds draft ─► frozen snapshot + sha256
   │                          ─► human decision ─► append-only audit
   │
   └─► Automation: terminal review ─► internal task ─► n8n webhook / mock
```

Next.js App Router · TypeScript · Supabase Postgres + pgvector · Vercel AI SDK ·
zod at every boundary · OpenAI `text-embedding-3-large` + `gpt-5-mini` +
`gpt-4o-mini-transcribe` · n8n via a controlled webhook · Playwright.

Model choices and their measured trade-offs: **[docs/model-selection.md](docs/model-selection.md)**.

## Run it locally

```bash
npm install && npx playwright install chromium
cp .env.example .env          # OPENAI_API_KEY, SUPABASE_URL, SUPABASE_SECRET_KEY
npm run db:push               # apply migrations
npm run ingest:products -- --embedding=openai
npm run dev                   # http://localhost:3000
```

Useful commands:

```bash
npm run validate:data          # products, cases, manifests against their schemas
npm run validate:ingestion     # database vs committed fixtures (read-only)
npm run ask -- "定期寿险有现金价值吗？"        # grounded answer from the CLI
npm run compare -- --a=doc_securerate5_v1 --b=doc_indexflex_ul_v1
npm run review -- --a=doc_securerate5_v1 --b=doc_indexflex_ul_v1 --case=DEMO-2026-003
npm run eval / eval:comparison / eval:workflow   # the frozen evaluations
npm test / test:db / test:ui
```

Deployment and environment variables: **[docs/deployment.md](docs/deployment.md)**.

One source of truth: `data/fictional-products/products.json`. The PDFs, the
manifest, the comparison cells and the evaluation ground truth are all derived
from it — the same number is never maintained by hand in two places.
