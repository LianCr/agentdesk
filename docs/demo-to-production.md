# Demo → Production

这份文档列的是 AgentDesk **现在不是什么**。

每一项都写清楚三件事:现在是什么样、真实生产需要什么、以及**为什么 Demo 这样取舍**。
内容来自 `docs/backlog.md` 与各阶段评估文档里已记录的限制,**没有新编的乐观说法**,
也没有隐去不好看的部分。

---

## 1. 安全与身份

### 没有认证,没有 RBAC

**现在**:线上 Demo 无登录。审核者署名是服务端写入的固定字符串 `"Demo Reviewer"`。
硬门只保证浏览器**无法**伪造或覆盖它。

**生产需要**:真实账号、角色(经纪人 / 主管 / 合规)、按角色限制审批权限、
会话管理、离职回收。审计记录里的"谁"必须是可追责的真人。

**为什么这样取舍**:Demo 的目的是让人 30 秒内看到产品,登录墙会挡住这件事。
CLAUDE.md 从一开始就规定"最多使用简单演示密码",不自建认证系统。

### 公开端点会消耗额度

**现在**:任何拿到 URL 的人都能调用 `/api/answer` 与 `/api/transcribe`,
两者都花 OpenAI 额度。没有限流、没有配额、没有滥用检测。

**生产需要**:认证后限流、按用户配额、异常调用告警、成本上限。

**为什么这样取舍**:这是"公开可点开"这个演示目标的直接代价。缓解措施是在 OpenAI
后台设月度支出上限。

---

## 2. 数据

### 全部是虚构数据,没有 PII 处理

**现在**:三款虚构产品、三个合成客户。系统从未接触过真实客户信息。

**生产需要**:PII 加密与访问控制、数据保留与删除策略、跨境传输合规、
向模型提供方发送客户数据前的处理与合同约束、可审计的数据流。

**为什么这样取舍**:红线之一就是"只使用公开或虚构数据"。用真实数据做作品集演示
本身就是错的。

### 生产与本地共用同一个数据库

**现在**:线上 Demo 与本地开发指向同一个 Supabase 项目。在本地跑 `npm run test:db`
时,线上看到的审核数据会同步变化(测试行会创建又删除)。

**生产需要**:环境隔离(dev / staging / prod),独立凭据,生产数据不可被开发流程触及。

**为什么这样取舍**:Demo 规模下多环境的运维成本大于收益。已记入 backlog
("Separate test/demo Supabase projects")。

---

## 3. 对外通信

### 没有对外发送客户沟通的能力

**现在**:自动化只能产生**内部任务**。`TaskType` 枚举里没有 client-facing 取值,
payload 里没有收件人字段。**这不是被禁用,是不存在。**

**生产需要**:如果业务确实要发客户邮件,需要:模板审批流、发送前人工确认、
退订与合规声明、送达与打开追踪、错发的召回预案,以及一套完全不同的责任模型。

**为什么这样取舍**:对一个会被误认为"AI 直接给客户发保险建议"的演示来说,
把这条路从**结构上**去掉,比加一堆守卫更可信。

### n8n 实机往返未经验证

**现在**:workflow 定义已提交(`n8n/agentdesk-post-review-task.json`,不含 URL 与
密钥)。本仓库未配置 `N8N_WEBHOOK_URL`,所以**真实的 n8n 往返从未跑通过**。
已验证的是完整的 mock 路径,以及用本地 mock webhook 服务器覆盖的投递 / 失败 /
畸形应答语义。

**生产需要**:真实实例、密钥轮换、投递监控、失败告警。

**为什么这样取舍**:为一个演示搭建并维护 n8n 实例,不如把 mock fallback 做成
一等路径——后者让 Demo 在任何环境下都能完整走通,且**明确标注未实际发送**。

### 重试策略刻意最小化

**现在**:手动重试,上限 3 次,无队列、无 worker、无退避。

**生产需要**:带退避的自动重试、死信队列、投递状态巡检。

**为什么这样取舍**:CLAUDE.md 禁止引入队列与 worker。一个按钮的演示不需要调度器。

## 4. 已知的行为缺口

### `allow_checklist_only` 仍可被人工批准

**现在**:M5 的状态机只看 `reviewState`,所以一份"事实无法核验"的比较**仍然可以
被点批准**。M5.1 在下游 fail closed——拒绝为它产生任何自动化(`FACTS_UNVERIFIED`)。

**生产需要**:审核界面本身就应该拒绝这个批准动作,而不是只在下游拦。

**为什么这样取舍**:发现时 M5 已冻结并通过评估;在下游 fail closed 是当时风险最小的
处理,并如实记入 backlog,而不是回头改动已验收的语义。

### `annuity_suitability` 没有对应的 ReviewFlag

**现在**:它是 Case C 案例设定里声明的风险标记之一,但 `ReviewFlag` 词表里没有语义
对应项。**没有**硬凑到一个意思不同的 flag 上。

**生产需要**:一个真正表达年金适合性审核的标记,及其触发规则。

**为什么这样取舍**:强行映射能让指标好看,但会让指标本身变成谎言。

### 语音识别准确率在真人语音上未验证

**现在**:API 路径用 macOS `say` 合成语音跑通(合成语音比自然语音更难识别):
英文 3/3 逐字正确,中文 2/3 正确(有一次把"有现金价值"听成"有限金价值")。
**浏览器麦克风实机测试从未运行**,因为构建环境没有麦克风。

**生产需要**:真人语音、多口音、嘈杂环境下的准确率评估。

**为什么这样取舍**:转写结果**从不自动提交**——正因为识别会错,才必须由人确认后
再提问。剩余错误率因此是一个复核步骤,而不是一个错误答案。

### INFRA-01:一次未复现的数据库套件失败

**现在**:M5-B 期间观察到一次 `test:db` 部分失败;之后所有运行(含两次针对性复现
尝试)都全绿。**根因未知,没有编造。**

**生产需要**:可观测性与告警,让这类间歇问题能被捕获而不是被重跑掩盖。

## 5. 性能与规模

### 自由提问需要 15–35 秒

**现在**:由推理型回答模型主导(检索与改写约 1–3 秒)。界面在等待时明确写出
"演示环境通常需要约 15–20 秒",不用假进度条。示例问题走预存的已核验回答,
0.09 秒返回,页面也明说这是预存回答。

**生产需要**:流式输出、更快的模型档位、或把校验后的部分结果先行呈现——但任何一项
都不能削弱"引用必须逐字核验"这条。

**为什么这样取舍**:两阶段架构(模型只出草稿,代码逐条校验引用)是这个产品的价值
所在。为了跑分去掉校验,等于把产品本身去掉。

### 检索规模

**现在**:3 份文档 / 20 页 / 45 chunks,顺序扫描已足够快,**没有建 ANN 索引**。

**生产需要**:文档量上到几千份时需要 HNSW/IVFFlat 索引、分片、以及重新校准的
检索评估。

**为什么这样取舍**:在 45 个 chunk 上建 ANN 索引只会让召回变差、复杂度变高。
已记入 backlog,等规模真的需要时再做。

### 没有生产监控

**现在**:错误只记错误码到服务端日志,不记堆栈、不记密钥、不记响应体。没有
APM、没有告警、没有仪表盘。

---

## 6. 合规

**演示里的规则不是法律结论。**65 岁阈值、replacement review、annuity suitability
都是本项目为**虚构产品**设定的业务政策。真实使用前必须由贵司合规人员、持牌经纪人
与适用法规共同确认。

**本项目不声称任何合规认证。**"本演示工作流内已批准"仅表示审核者认可了本演示工作
流中的一个内部步骤,不构成适合性判断、承保方核准、合规或法律批准、报价有效性,
也不构成购买建议。

---

## 这个 Demo 真正证明了什么

不是"这套系统可以直接上线"。

是:**在 AI 参与保险业务的地方,哪些东西必须由确定性代码拥有** —— 引用的真实性、
不排名、事实层的四态不塌缩、被审对象的不可变性、审计的不可改写、以及"能不能发给
客户"这件事本身。

这些边界在这里是**可验证的**:41 例工作流评估 19 项硬门全零、23 例比较评估 17 项
硬门全过、变异测试证明评估器确实会失败。把它们接到真实数据与真实身份上,是工程量;
把它们从架构里拿掉,才是风险。
